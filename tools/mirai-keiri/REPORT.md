## 1. 結論：LLM は要らない

# NO
# NO
# NO

請求書から振込ファイルを作る工程に、LLM は**一箇所も必要ない**。
Ollama もクラウドのモデルも要らない。

理由は「使わないほうが安全だから」ではなく、**この工程に推論が存在しないから**である。

| 工程 | 必要な処理 | LLM |
|---|---|---|
| 1. 新共有のファイル検知 | ディレクトリ監視 | 不要 |
| 2. 請求書から金額を取る | 業者ごとの定型解析 | 不要 |
| 3. 支払先 → 口座情報 | マスタ参照（完全一致） | **使ってはいけない** |
| 4. 支払先ごとに合算 | 整数の足し算 | 不要 |
| 5. 全銀ファイル生成 | 固定長の文字列整形 | 不要 |
| 6. 振込一覧表の出力 | 表の書き出し | 不要 |
| 7. FB-Web に送信 | **人間** | — |

工程3〜6は全部、入力が決まれば出力が一意に決まる関数である。
LLM を挟むと、同じ入力から違う出力が出る可能性が生まれる。
それは**改善ではなく劣化**にあたる。

### ただし2点、正確に切り分けておく

**(a) 紙・スキャンPDFなら OCR は要る。OCR は LLM ではない。**
Tesseract / PaddleOCR はパターン認識であって生成モデルではない。
OCR を入れる場合も、読み取った金額は請求書の合計欄と突合して一致を確認する。
一致しなければ人間に上げる。OCR の出力をそのまま信じる設計にはしない。

**(b) LLM を使う余地があるのは「初見の業者の請求書のどこに金額があるか」を
当てる部分だけで、そこも本番の金の経路には入れない。**
新規業者はどのみち口座確認（`verified_by`）で人間が一度触る。
その一度の作業を数分短縮するために、生成AIを経理システムに常駐させる価値はない。

### 契約上、これは選択ではなく要件

別章第5条第1項（個人データは院内閉鎖環境で完結）・
第6条第1項（個人データを生成AIに入力しない）がある。
請求書には検査委託や給食などで**患者名が載っていることがある**。
「請求書だから個人データではない」とは言い切れない。

決定論的に組めば、この論点そのものが消える。
`tests/test_offline_guarantee.py` が、ネットワークとAIモジュールを
import していないことをAST検査し、さらにソケットを塞いだ状態で
全工程が完走することを機械検査する。**これは検査基準にそのまま引用できる。**

## 3. 全銀フォーマット（総合振込・種別コード21）

全レコード **120バイト固定長・半角・Shift_JIS**。
ヘッダー(1) → データ(2)×N → トレーラー(8) → エンド(9)。

## 4. 事故が起きるのはここ

金額の計算ではなく、**文字と桁**で事故が起きる。

### 濁点は1文字を2バイト消費する
`ガ` → `ｶﾞ`。「ｶﾞ」16文字の名義は32バイトで、30バイトの受取人名欄に入らない。
実装では**切り詰めずエラーで停止**する。切り詰めると別人の口座名義になる。

### 小書き文字は大文字に直す
`ｷｬﾉﾝ` → `ｷﾔﾉﾝ`。全銀の記入規則。変換したことは一覧表に出す。

### 漢字からカナを自動生成してはいけない
「東」は ﾋｶﾞｼ か ｱｽﾞﾏ か、機械には決められない。
`payee_name_kana` は**先方の振込先案内・通帳の表記をそのまま**マスタに入れる。
実装は漢字を受け取ると変換せずエラーにする。
名義相違は組戻し手数料と入金遅延に直結する。

### 口座情報は請求書から取らない
請求書のフッタの口座番号をOCRで読んで振り込む設計は、**請求書を偽造すれば
金が動く**設計である。口座はマスタのみ、マスタは `verified_on`/`verified_by`
が埋まっていなければ処理が止まる。

### 金額は必ず整数（円）
`float` を受け取るとエラーにする。丸め誤差の入る余地を型で塞ぐ。

### 同じ請求書を二度払わない
`invoice_no` の重複を検出したら停止する。

## 5. 運用フロー（案）

```
新共有/請求書/2026-10/ にPDFが保存される
        ↓  ディレクトリ監視（または月次で手動実行）
    請求書明細 CSV に1行追加     ← 定型解析 or 手入力。ここは人が直せる形にしておく
        ↓
    振込先マスタと突合（未登録・口座未確認なら停止）
        ↓
    支払先ごとに合算 ＋ 2σ 異常検知
        ↓
 ┌──────────────────────────┐
 │ 振込一覧表 .xlsx  ← ★ 人間の承認点 │
 └──────────────────────────┘
        ↓ 承認・押印
    全銀ファイル .txt（独立検証器を通過したものだけ）
        ↓
    人間が FB-Web にアップロード・都度確認番号で承認
```

**振込一覧表が唯一の統制点。** ここに載る合計金額は、トレーラーレコードに
書き込まれる整数と同一の値である。一覧表を承認することは、ファイルを承認すること
と等価になるよう設計してある。

### 2σ異常検知
支払先ごとの過去実績から平均と標準偏差を出し、2σを超えた支払先を一覧表に
フラグする。初回の支払先、毎回同額だった先の金額変更も同様。
統計計算のみでモデルは使わない。フラグは処理を止めず、承認者の目を向けさせる。

**確認できていないこと（要対応）**

2. **委託者コード** — 銀行から払い出される値。FB-Web の契約書類で確認

   別サービスと思われる。監視方式は実体を見てから決める
4. **請求書の実物** — 業者ごとのレイアウトが未確認。§1(a) の解析方式は実物を見て確定
5. **FB-Web 側の上限** — 1ファイルあたりの件数上限・取組日の受付期限
6. **手数料負担の実態** — 業者ごとの先方/当方負担を契約書で確認しマスタに入れる

**スコープの注意**

## 7. 次の一手

1. 中村先生から **FB-Web の総合振込マニュアル（紙 or PDF）** を1部もらう → §3の3点を確定
2. **請求書の実物を5〜10通** 見せてもらう → 解析方式を確定（ここで初めて OCR の要否が決まる）
3. **振込先マスタを人間が1回作る** — これが全体で一番重要な作業。
   業者数はおそらく20〜40。一度作れば以降は差分だけ
4. 実データ1ヶ月分で **並行運用** — 手作業の結果と生成ファイルを突合し、
   完全一致を確認してから切り替える
5. 切り替え後も **FB-Web への送信は人間が行う**。ここは自動化しない
